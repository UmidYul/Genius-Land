# CLAUDE.md

Guidance for Claude when working in this repository.

## Project

**Genius Land** — новая платформа управления частной школой Genius Land (два филиала, 1–11 классы, ~700–800 учеников). Электронный журнал + администрирование + оплата обучения + уведомления (Telegram-бот, SMS, e-mail).

Что делаем, для кого и какие роли — в **`PRODUCT.md`**. Читай его перед любой задачей.

Общение с владельцем (Umid) — на русском.

## Главные правила

### 1. Это совершенно новый продукт
Мы **не копируем** старый сайт geniusland.uz. Архитектура, схема БД, код, тексты интерфейса и дизайн создаются заново. Старая система во многом не доделана и содержит ошибки (особенно финансы — см. `Legacy Website Audit/H_technical_observations.md`).

### 2. Legacy — только справочник, и всё из него подтверждается
Папка `Legacy Website Audit/` — аудит старого сайта: функции, бизнес-правила (`D_business_rules.md`, ID вида `BR-xxx`), роли и права, найденные ошибки, открытые вопросы.

- Её можно использовать, чтобы находить идеи, бизнес-правила, ограничения и функции.
- **Каждый раз, когда берёшь что-то из legacy (правило, ограничение, формулу, функцию, статус, поле, идею), сначала спроси Umid, можно ли применить это в новом проекте.** Не внедряй до явного «да».
- В вопросе указывай источник (файл и ID, например `D_business_rules.md BR-023`), суть в одной строке и что предлагаешь — как есть, изменить или не брать.
- Подтверждённые и отклонённые решения записывай в `docs/legacy-decisions.md`, чтобы не спрашивать повторно.
- Если правило из legacy противоречит `PRODUCT.md` или словам Umid — приоритет у `PRODUCT.md` и Umid.

### 3. Не додумывай открытые решения
Список открытых решений — в `PRODUCT.md` → «Open decisions». Если задача от них зависит — спроси, а не выбирай молча.

### 4. Ключевые особенности домена (не забывать)
- **Два филиала, изоляция данных.** У каждой записи, принадлежащей филиалу, есть филиал. Оба филиала видит только основатель (суперадмин — на техническом уровне). Директор, администратор и учитель — только свой филиал.
- **8–11 классы учатся только в группах по направлениям** («ЭКОНОМИКА 1», «МЕДИЦИНА 2», «ФИЛОЛОГИЯ 1»). Группа = полноценный класс (свой классный руководитель, расписание, журнал) с учениками разного возраста. В модели это один и тот же «класс» с типом `REGULAR` (1–7) или `DIRECTION_GROUP` (8–11); номер класса ученика 8–11 — только атрибут.
- **Учебная неделя:** 1–7 — пн–пт; группы 8–11 — пн–сб (суббота до обеда). Рабочий ли день — зависит от типа класса.
- **Родители и ученики не имеют веб-страниц.** Только API для будущего приложения и Telegram-бот.
- **Уведомления: Telegram-бот — основной канал.** Коды входа — всегда во все подключённые каналы, включая SMS. В остальном **SMS — редко** (напоминания об оплате и редкие важные сообщения).
- **Основатель утверждает важное, а не каждую мелочь.** Какие действия требуют утверждения — настройка, а не код.
- **Бизнес-правила с цифрами (цены, скидки, сроки) — настройки**, которые можно менять без релиза.
- **Бот показывает расписание только на сегодня и завтра**, всегда из актуальных данных (без кеша, который может устареть).
- Роли v1: основатель, директор, администратор, учитель, бухгалтер, суперадмин (базово), родитель, ученик. Позже: отдел кадров, завхоз. Права — данные (действие + область видимости), меню и API выводятся из прав.
- Интерфейс узбекский (латиница) и русский, без захардкоженных строк. Часовой пояс Asia/Tashkent.
- Не выдумывать реальные данные (имена, оценки, суммы). Плейсхолдеры помечать явно.

## Stack

Next.js 15 (App Router) + TypeScript strict, PostgreSQL 16 + Prisma 6, next-intl 4 (uz/ru), Tailwind CSS 4, pg-boss 10, Vitest, Playwright. pnpm 9 монорепо, Node 22+. Подробнее — `PRODUCT.md` → Stack и `docs/v1/PLAN.md` §2.

## Development Commands

Первый запуск: `cp .env.example .env && pnpm i && docker compose up -d && pnpm db:migrate && pnpm dev` (кабинет — http://localhost:3000 → `/uz`).

- `pnpm dev` — web (порт 3000) + worker параллельно.
- `pnpm build` — сборка web и worker.
- `pnpm lint` (`lint:fix`), `pnpm format` (`format:check`), `pnpm typecheck`.
- `pnpm test` — unit + интеграционные; `pnpm test:unit`, `pnpm test:int`. Один файл: `pnpm vitest run packages/core/src/money.test.ts`; один тест: добавить `-t "<название>"`.
- `pnpm test:e2e` — Playwright: пересоздаёт и засеивает **тестовую** БД, поднимает dev-сервер на 3100 с ней, коды входа читает из `test-results/e2e-outbox.jsonl`; проекты `phone-360` и `desktop`. Браузер: `pnpm exec playwright install chromium`.
- `pnpm db:migrate` — применить миграции; `pnpm db:migrate:dev --name <имя>` — создать миграцию; `pnpm db:seed`; `pnpm db:studio`.
- Перед PR: `lint`, `format:check`, `typecheck`, `test` — CI (`.github/workflows/ci.yml`) гоняет то же самое + `build`.

## High-Level Architecture

```
apps/web       Next.js: кабинет сотрудников (app/[locale]/…) + /api/v1 (будущее приложение)
apps/worker    Node-процесс: pg-boss (очереди и cron), позже Telegram-бот (этап 6)
packages/core  вся бизнес-логика и правила — UI и бот только вызывают её
packages/db    Prisma: схема, миграции, клиент (`prisma`, тип `Db` = клиент или транзакция), сид
packages/i18n  словари uz/ru + `translate()` для кода вне React
packages/ui    дизайн-система: токены цветов (tokens.css), Tailwind theme (theme.css), компоненты
```

- **Пакеты отдают TypeScript-исходники** (без сборки): web транспилирует их через `transpilePackages`, worker бандлит через tsup. Импорты между пакетами — `@gl/core`, `@gl/db`, `@gl/i18n`, `@gl/ui`; внутри web — алиас `@/*`.
- **Клиентские компоненты не импортируют корень `@gl/core`** (он тянет Prisma). Для браузера есть подпути: `@gl/core/time`, `@gl/core/money`, `@gl/core/result`.
- **Ошибки**: доменные функции возвращают `Result<T>` (`ok`/`err`) с кодом из `errorCodes`; текст — `errors.<CODE>` в словарях (тест проверяет, что у каждого кода есть перевод на обоих языках). `DomainError` — для мест, где Result вернуть нельзя.
- **Деньги** — `bigint` в целых сумах (`parseSum`, `formatSum`, `percentOf` с округлением half-up). **Время** — хранится в UTC; границы дня/месяца, формат `ДД.ММ.ГГГГ` и день недели — по Asia/Tashkent (`dayRange`, `monthRange`, `formatDate`…). Не использовать `Date#getDate()` и т. п. для школьных дат.
- **Аудит**: `writeAudit(db, actor, entry)` в той же транзакции, что и изменение. Таблица `AuditLog` только на добавление (триггер в БД запрещает UPDATE/DELETE).
- **Настройки**: каждая настройка объявляется через `defineSetting({ key, schema, defaultValue, scope })`; в БД хранятся только отличия от значения по умолчанию. Чтение: значение филиала → глобальное → по умолчанию. В web — `getSettings()` (`apps/web/src/lib/settings.ts`, кеш на запрос); запись — `updateSetting()` (валидирует и пишет аудит). Уникальность `(key, branchId)` с `NULLS NOT DISTINCT` — вручную в миграции.
- **i18n**: все URL с префиксом `/uz` или `/ru` (middleware next-intl). Ключи типизированы (`apps/web/src/global.d.ts`). ESLint `i18next/no-literal-string` запрещает текст в JSX и в `aria-label`/`title`/`alt`/`placeholder`/`label` — в `apps/web` и `packages/ui`. Компоненты `packages/ui` получают все тексты пропсами.
- **Тема и цвета**: цвета только токенами (`bg-surface`, `text-fg-muted`, `bg-primary-solid`, …); стандартная палитра Tailwind отключена. Тёмная тема — `<html data-theme="dark">`; выбор (светлая/тёмная/системная) хранится в localStorage, скрипт в `<head>` применяет его до первой отрисовки.
- **Шрифты**: Sora — заголовки (`font-head`), Manrope — текст. У Sora нет кириллицы — русские заголовки автоматически берут глифы Manrope.
- **Каркас кабинета**: `apps/web/src/components/shell/` — боковое меню (≥1024 px), выезжающее меню на телефоне (`<dialog>`), верхняя панель (язык, профиль с выбором темы). Меню статическое (`nav-items.ts`) — на этапе 1 строится из прав.
- **Доступ (этап 1)**: права — реестр `packages/core/src/access/permissions.ts` (`модуль.ресурс.действие`), роли — `roles.ts`; сид синхронизирует их в БД (`syncAccessModel`). `loadActor()` собирает права пользователя по назначениям ролей и филиалам. Проверка одной записи — `can(actor, право, { branchId, classId, studentId, ownerUserId })`, списки — `scopeWhere(actor, право, { branch: branchId, … })`.
- **Сервисы с данными филиалов** принимают `ServiceContext` (`createServiceContext`): актор обязателен, а `ctx.db` — клиент с защитой (`access/guard.ts`). Список или подсчёт модели из `branchOwnedModels` без условия на филиал бросает `UnscopedQueryError`. **Каждую новую модель филиала добавляй в `branchOwnedModels`**, а новое право — в реестр (матрица тестов подхватит его сама).
- **Области ASSIGNED / HOMEROOM / CHILDREN / SELF** берут данные из `ScopeRelationsProvider` (`access/actor.ts`); в этапе 1 это заглушка с пустыми наборами — этапы 2 и 4 подключают реальные классы, учеников и назначения.
- **Web-авторизация**: `apps/web/src/lib/auth.ts` — `getAuth()` (сессия + актор + контекст на запрос), `requireAuth()`, `requirePermission()` (без права — 404). Middleware только перенаправляет без cookie; настоящая проверка — на сервере в каждой странице и в каждом действии. Пункты меню — `components/shell/nav-items.ts`, у каждого своё право.
- **Уведомления**: `NotificationDispatcher` (`packages/core/src/notifications`). Коды (`critical: true`) уходят во все подтверждённые каналы, включая SMS. Сейчас провайдеры — заглушки `ConsoleSms`/`ConsoleEmail` (лог + `DEV_OUTBOX_FILE`); реальные подключаются в `apps/web/src/lib/notify.ts` на этапе 6.
- **Сид** — `packages/core/src/seed` (`pnpm db:seed`): права, роли, два филиала и демо-пользователи (не в production). Пароль демо-сотрудников — `demo12345`, телефоны `+99800000000N`.
- **Структура школы (этап 2)**: `packages/core/src/school` (годы и четверти, календарь, справочники, классы, Excel) и `packages/core/src/people` (сотрудники, ученики, родители). Класс 1–7 и группа 8–11 — одна модель `Class` (`REGULAR` / `DIRECTION_GROUP`); правило номера класса — `checkGradeForClass`. Вместимость проверяется под блокировкой строки класса (`SELECT … FOR UPDATE`).
- **`isSchoolDay(db, класс, дата)`** (`school/calendar.ts`) — единственный источник ответа «учебный ли день»: внутри четверти, исключения календаря (свой филиал важнее общего, свой тип класса важнее «всех»), иначе неделя по типу класса. Посещаемость, журнал и бот должны использовать её.
- **Области на реальных данных**: `dbScopeRelationsProvider` (`access/relations.ts`) — по умолчанию в `loadActor`. ASSIGNED: для записей **с предметом** — только пары «класс × предмет», которые учитель ведёт; для записей уровня класса (ученики, расписание) — ещё и класс, где он классный руководитель. **Поэтому сервисы оценок и тем (этап 4) обязаны передавать `subjectId` в `can()`.**
- **Сотрудник ↔ учётная запись** связываются по телефону: при создании сотрудника и при создании пользователя суперадмином (`linkStaffToUser`). Родитель — пользователь с ролью PARENT без пароля; один телефон = один человек.
- **Excel**: шаблоны, разбор и импорт — `school/excel`; заголовки и значения распознаются на обоих языках. Импорт: предпросмотр сохраняется в `ImportJob`, при подтверждении строки проверяются заново и все верные создаются одной транзакцией. Выгрузки (`/api/export/[kind]`) используют те же функции списков, что и страницы, — права и фильтры совпадают.
- **Формы в web**: `Form` из `components/form.tsx` вместо `<form action>` (React 19 сбрасывает поля после отправки, и при ошибке пропадает ввод). Диалоги с формой — `DialogForm` из `components/action-form.tsx`.
- **Тесты**: `*.test.ts` — unit; `*.int.test.ts` — интеграционные, работают с `DATABASE_URL_TEST` (миграции применяются автоматически в `test/integration-setup.ts`, файлы выполняются последовательно).

# Документ I. Спецификация новой независимой системы

## 1. Принципы
1. Реализуем **функциональность** (что делает система), а не копируем код. Ни один файл старой системы не используется: архитектура, схема БД, тексты и дизайн создаются заново.
2. Исправляем найденные дефекты (H §3) с первого дня — особенно в финансах.
3. Права — единственный источник истины: меню, страницы и API выводятся из матрицы прав (без отдельных списков `allowedRoles`).
4. Деньги — только через леджер (проводки); счета, долг, аванс и отчёты — производные от него.
5. Всё, что меняет деньги, оценки или статусы, пишет аудит (кто, когда, было/стало, причина).

## 3. Модель данных
За основу берётся концептуальная модель (Документ E) со следующими изменениями:
- **Ledger:** `account` (на ученика) + `ledger_entry` (debit / credit, сумма > 0, ссылка на документ). Баланс = Σ проводок. Счёт = документ начисления; платёж = документ поступления; **allocation** (платёж ↔ счёт, сумма) — для частичных оплат, авансов и автозачёта.
- Деньги — `bigint` в тийинах или `numeric(14,2)`; запрет отрицательных сумм на уровне CHECK.
- Уникальности: (student, period) у счёта; (student, date[, lesson]) у посещаемости; ПИНФЛ; телефон пользователя; код класса в рамках года.
- **Enrollment-история** с первого дня (ADMITTED при создании).
- **Term** (четверти) создаются вместе с учебным годом.
- Все справочники (категории тарифов, типы нарушений, типы оценок) — таблицы-справочники вместо разных enum-ов на разных экранах.
- Мягкое удаление `deleted_at` + аудит; жёсткое удаление — только SUPER_ADMIN через отдельную процедуру.

## 5. Нефункциональные требования
- **Производительность:** ~1 000 учеников + ~1 500 родителей; p95 API < 300 мс; журнал класса < 1 с.
- **Безопасность:** argon2 / bcrypt для паролей; единая политика (≥ 8, буквы + цифры); блокировка после 5 неудач на 15 мин; refresh-token в httpOnly-cookie (web); rate-limit на вход и OTP; аудит всех изменений денег, оценок, статусов и прав; маскирование PII в логах; ПДн (Закон РУз «О персональных данных») — хранение на сервере в Узбекистане.
- **Резервное копирование:** ежедневный pg_dump + WAL-архив, хранение 30 дней, еженедельная проверка восстановления, копия вне сервера; файлы — ежедневный sync.
- **Наблюдаемость:** health-check, логи (pino), метрики, алерты по ошибкам SMS и баланса SMS.
- **Локализация:** узбекский (латиница) — основной; русский — второй; формат дат ДД.ММ.ГГГГ; валюта UZS; часовой пояс Asia/Tashkent (все месячные границы — по Ташкенту).
- **Доступность и UX:** тёмная тема, мобильная адаптивность, сохранённые фильтры, экспорт из каждого реестра.

## 6. Обработка ошибок и формат API
Единый конверт: `{ success, data, error: {code, message, details[]}, meta: {page, pageSize, total} }`; коды 400 (валидация, со списком полей), 401, 403 (нет права или scope), 404, 409 (конфликт и уникальность), 422 (бизнес-правило), 429. Все тексты ошибок — из словаря i18n. Идемпотентность для платежей и массовых операций (`Idempotency-Key`).

## 7. Миграция данных
Законный путь — выгрузки, доступные владельцу в интерфейсе: «Eksport» учеников (xlsx, financial-xlsx), пользователи, учителя, «Ma'lumot eksporti» в /system-health, отчёты каталога (CSV / Excel). План: выгрузить → очистить (дубли, номера-заглушки +99800…, конфликты расписания) → загрузить импортёром новой системы → сверить счётчики (629 учеников, 69 учителей, 37 классов, 20 предметов, 393 урока).

## 8. Стратегия тестирования
- Unit: формулы (леджер, скидки, пропорции, средние, скоринг, удержания) — 100 % веток.
- Интеграционные: каждый сценарий из Документа F как автотест API (Jest + supertest + тестовая БД).
- RBAC-тесты: матрица «роль × endpoint» генерируется автоматически из реестра прав.
- E2E (Playwright): ключевые потоки — зачисление, отметка посещаемости, выставление оценки, счёт → оплата → квитанция, договор → подпись.
- Приёмка: прогон на копии реальных данных; сверка отчётов со старой системой за один месяц.

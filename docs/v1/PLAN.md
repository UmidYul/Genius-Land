## 1. Цель v1

Сотрудники обоих филиалов полностью ведут учебный день и оплату в новой системе:
- учитель за секунды отмечает посещаемость, ставит оценки и тему урока с телефона;
- администратор ведёт классы, группы 8–11, расписание и списки учеников;
- бухгалтер ведёт договоры, счета, платежи и долги;
- директор видит свой филиал, основатель — оба и утверждает важное;
- родители и ученики получают уведомления, коды и расписание на сегодня/завтра в Telegram-боте; напоминания об оплате — по SMS.

Не входит в v1: веб-страницы для родителей и учеников, мобильное приложение, HR, завхоз, питание, автобус, поездки, домашние задания, чат, онлайн-оплата (Click/Payme), интерфейс дисциплины.

## 2. Архитектура [предложение]

### 2.1 Структура репозитория — pnpm-монорепо

```
apps/
  web/        Next.js (App Router) — кабинет сотрудников + /api/v1 для будущего приложения
  worker/     Node-процесс: Telegram-бот (grammY) + фоновые задачи (pg-boss)
packages/
  db/         Prisma: схема, миграции, сиды
  core/       доменная логика и правила (сервисы, права, деньги, расписание) — без UI
  i18n/       словари uz (латиница) / ru, общие для web, бота и шаблонов уведомлений
  ui/         дизайн-система (компоненты, токены)
```

Почему так:
- **Вся бизнес-логика в `packages/core`.** Её вызывают серверные действия Next.js, `/api/v1` для будущего приложения и бот. Правило пишется один раз.
- **Отдельный `worker`.** Бот и фоновые задачи (автосчета 1-го числа, напоминания, рассылки) не должны жить внутри Next.js.
- **pg-boss вместо Redis.** Очереди хранятся прямо в PostgreSQL — меньше сервисов на одном сервере.

### 2.2 Технологии

| Задача | Выбор |
|---|---|
| Web | Next.js App Router, TypeScript strict, Server Actions для форм, React Server Components |
| Стили | Tailwind CSS + собственные компоненты в `packages/ui` |
| Формы и валидация | zod (общие схемы для web, API и бота) + react-hook-form |
| БД | PostgreSQL 16 + Prisma |
| i18n | next-intl (web), тот же словарь из `packages/i18n` для бота и SMS/e-mail |
| Аутентификация | Свои сессии в БД (httpOnly cookie для web, bearer-токен для API приложения), argon2 |
| Telegram | grammY |
| Очереди и cron | pg-boss |
| SMS | Адаптер `SmsProvider` (провайдер — открытый вопрос; для разработки — провайдер-заглушка, пишущий в лог) |
| E-mail | Адаптер `EmailProvider` (SMTP) |
| Excel | exceljs (импорт и экспорт) |
| Тесты | Vitest (unit и интеграционные с тестовой БД), Playwright (E2E ключевых потоков) |
| Качество | ESLint, Prettier, typecheck, GitHub Actions на каждый PR |
| Деплой | Docker Compose (web, worker, postgres, nginx), ежедневный pg_dump вне сервера; сервер в Узбекистане (закон о персональных данных) |

### 2.3 Сквозные правила
- **Деньги** — целые числа в сумах (`BigInt`), CHECK на неотрицательность там, где сумма не может быть отрицательной.
- **Время** — хранится в UTC, все границы дней, недель и месяцев считаются по Asia/Tashkent.
- **Мягкое удаление** (`deletedAt`) для людей, классов и финансовых документов. Жёсткое удаление — только у суперадмина.
- **Аудит**: всё, что меняет деньги, оценки, посещаемость задним числом, статусы учеников, права и настройки, пишет запись «кто, когда, было/стало, причина».
- **Без захардкоженных строк**: все тексты из словаря uz/ru. Тексты ошибок — коды + перевод.
- **Настройки вместо констант**: цены, скидки, сроки, окна правки, пороги — в таблицах настроек и политик.

### 2.4 Решения этапа 0 (реализовано)
- **Настройки**: объявляются в коде (`defineSetting`: ключ, zod-схема, значение по умолчанию, область «глобально / филиал»); в БД хранятся только изменённые значения. Порядок чтения: филиал → глобально → по умолчанию. Каждое изменение пишет аудит.
- **AuditLog только на добавление** — триггер в БД запрещает UPDATE и DELETE.
- **Меню на телефоне** — выезжающее (не нижняя панель): после этапа 1 пунктов меню будет больше, чем помещается в нижнюю панель.
- **Тема** (светлая / тёмная / системная) хранится в браузере (localStorage). Перенос в профиль пользователя — по желанию после этапа 1.
- **Шрифты**: у Sora нет кириллицы, русские заголовки рисуются Manrope (см. `docs/BRAND.md`).

### 2.5 Решения этапа 1 (реализовано)
- **Права — данные.** Реестр прав `модуль.ресурс.действие` и роли v1 описаны в `packages/core/src/access/` и синхронизируются в БД сидом; во время работы права читаются из БД. Меню и страницы выводятся из прав.
- **Изоляция филиалов — в двух слоях:** `can(actor, право, запись)` для одной записи и `scopeWhere(...)` для списков. Сервисы получают клиент БД с защитой: список/подсчёт по данным филиала без условия на филиал падает с ошибкой.
- **Переключатель филиала** сужает показ, но никогда не расширяет права. «Все филиалы» — только у тех, у кого есть `ALL_BRANCHES`/`SYSTEM`. Выбор хранится в профиле.
- **Вход:** телефон + пароль (argon2id); с нового устройства — 6-значный код во все подключённые каналы, включая SMS; после этого устройство доверенное (httpOnly-cookie). Временный пароль от суперадмина нужно сменить при первом входе.
- **Защита от повышения привилегий:** роль выдаётся или снимается, только если её уровень не выше своего; последнего активного суперадмина нельзя снять или заблокировать.
- **Утверждения:** основатель утверждает только заявки уровня «основатель» — заявки директора его не беспокоят (решение Umid, 24.10.2026). Политика `ApprovalPolicy` определяет, кто утверждает заявку данного типа (основатель или директор филиала). Свою заявку утвердить нельзя; отказ — только с причиной. Модуль регистрирует обработчик, который применяет изменение в той же транзакции. Типов заявок пока нет — появятся в этапах 4–5.
- **API приложения (заготовка):** короткий подписанный access-токен (15 мин) и refresh-токен с ротацией; `/api/v1/me`, `/api/v1/auth/refresh`.


### 2.6 Решения этапа 2 (реализовано)
- **Учебный год — у филиала**, создаётся сразу с четырьмя четвертями; текущий год у филиала один (частичный уникальный индекс). Каникулы — промежутки между четвертями.
- **Календарь**: исключения «праздник» и «рабочий день (перенос)» — на филиал или на оба, для всех классов или одного типа. Запись «на оба филиала» может сделать только тот, кто управляет календарём каждого филиала; в v1 такой роли нет, поэтому каждый директор ведёт календарь своего филиала.
- **Справочники** предметов и направлений — общие для школы. В сиде — направления из PRODUCT.md (Экономика, Медицина, Филология); предметы вводятся в интерфейсе.
- **Класс**: тип не меняется после создания; вместимость нельзя уменьшить ниже числа учеников; в архив — только пустой класс. Классный руководитель обязателен.
- **Ученик**: номер GL-XXXXXX из последовательности БД (сквозной, не переиспользуется). Возможный дубль (имя + дата рождения) — предупреждение с подтверждением; номера учеников чужого филиала не показываются. Выбывший ученик не занимает место в классе.
- **Права**: добавлены `people.staff.view`/`manage` — директор и администратор (свой филиал), основатель — просмотр.
- **Excel**: свои шаблоны; импорт только верных строк одной транзакцией; строки с возможными дублями учеников не импортируются — их добавляют вручную.

## 3. Модель данных v1 (ключевые сущности)

### 3.1 Организация и люди
- **Branch** — филиал.
- **User** — учётная запись: телефон (уникальный, +998…), e-mail, пароль (только у сотрудников), язык интерфейса, статус, счётчик неудачных входов и время блокировки.
- **RoleAssignment** — пользователь ↔ роль ↔ набор филиалов. Пример: бухгалтер с одним или двумя филиалами; основатель — все филиалы.
- **Staff** — профиль сотрудника (ФИО, должность, филиал). Учитель — сотрудник с ролью «учитель».
- **Student** — ученик: номер `GL-` + 6 цифр, ФИО, дата рождения, пол, филиал, класс, номер класса 1–11 (для 8–11 — атрибут), статус (активен, выбыл, выпущен, переведён) с историей.
- **Guardian** — родитель/опекун; связь с учеником (кто кому, главный контакт).
- **NotificationChannel** — подключённые каналы пользователя: Telegram chat id, телефон для SMS, e-mail; признак подтверждения.

### 3.2 Права
- **Permission** — код `модуль.ресурс.действие`, например `finance.payment.reverse`.
- **Role** → набор пар (право, область видимости).
- **Области видимости:** `SYSTEM` (технически всё), `ALL_BRANCHES`, `BRANCH` (филиалы из назначения), `ASSIGNED` (классы и предметы, которые ведёт учитель), `HOMEROOM` (класс, где он классный руководитель), `SELF`, `CHILDREN`.
- Проверка — в `packages/core` для каждой операции + фильтр запросов к БД по области. Меню строится из прав.

### 3.3 Учебная структура
- **AcademicYear** + **Term** (четверти) — создаются вместе.
- **WorkCalendar** — праздники и переносы; правило рабочих дней по типу класса (1–7: пн–пт; группы 8–11: пн–сб).
- **BellSchedule** — сетка звонков; отдельная для будней и для субботы групп 8–11.
- **Subject** — предмет.
- **Class** — единая учебная единица:
  - `type = REGULAR` — 1–7 класс, `gradeLevel` 1–7, название «5-А»;
  - `type = DIRECTION_GROUP` — группа 8–11, название «ЭКОНОМИКА 1», направление, ученики разных классов 8–11;
  - филиал, учебный год, вместимость, **классный руководитель**.
- **Direction** — справочник направлений (Экономика, Медицина, Филология…).
- **TeachingAssignment** — учитель × класс × предмет.

### 3.4 Расписание
- **TimetableSlot** — класс × день недели × номер урока × предмет × учитель × кабинет, срок действия.
- **TimetableChange** — разовые изменения на дату: замена учителя, отмена урока, перенос, смена кабинета. Бот и журнал показывают расписание на дату = шаблон + изменения.
- Конфликты (учитель, кабинет, класс в одно время) **блокируют сохранение**.

### 3.5 Журнал
- **Lesson** — конкретный урок на дату (из расписания с учётом изменений): тема, учитель, кто провёл.
- **AttendanceMark** — отметка ученика (присутствовал, отсутствовал, опоздал, уважительная причина, болеет). Единица учёта — открытый вопрос (см. §6).
- **Grade** — оценка: ученик, урок/предмет, значение в пределах шкалы, тип, автор, статус (активна/аннулирована), история изменений с причиной.
- **GradingScale** — шкала как настройка [предложение: 5-балльная, 2–5].
- **TermGrade** / **YearGrade** — итоговые: расчётное значение, выставленное значение, статус (черновик, утверждена, заблокирована).

### 3.6 Финансы
- **TuitionPolicy** — политика оплаты на учебный год (изменяемая, с историей версий): месячная плата, месяцы оплаты (сен–май), скидка за годовую предоплату и дата, скидка за второго ребёнка, день выставления счёта, срок оплаты, напоминание за N дней. Стартовые значения — из правила 13.
- **Contract** — договор ученика на учебный год: план оплаты (помесячно / годовая предоплата), применённые скидки, статус.
- **Discount** + **StudentDiscount** — скидки (процент 0–100 или сумма), с утверждением, если требуется.
- **Account** (лицевой счёт ученика) + **LedgerEntry** (дебет/кредит, сумма > 0, ссылка на документ). Баланс = сумма проводок.
- **Invoice** — начисление за месяц (уникально: ученик + месяц), строки.
- **Payment** — поступление: сумма, способ (наличные, карта, перечисление), квитанция `RCP-…`, кто принял.
- **Allocation** — распределение платежа по счетам. Аванс автоматически гасит следующие счета.
- **Reversal** — сторно платежа или счёта с причиной; удаления нет.

### 3.7 Утверждения
- **ApprovalPolicy** — какие действия и при каких условиях требуют утверждения и кем (директор филиала / основатель).
- **ApprovalRequest** — заявка: тип, данные, автор, статус, кто и когда решил, комментарий.

[предложение] Стартовый список утверждений основателем: индивидуальная скидка выше настраиваемого порога; сторно платежа; списание долга; изменение политики оплаты. Директор филиала утверждает: остальные скидки; разблокировку итоговых оценок. Мелочи (правка оценки с причиной, перенос урока) утверждения не требуют.

### 3.8 Уведомления
- **NotificationTemplate** — шаблон события на uz/ru для каждого канала.
- **NotificationRule** — какое событие в какие каналы идёт (бот / SMS / e-mail), кому.
- **Notification** + **Delivery** — сообщение и попытки доставки по каналам со статусами.
- Правила маршрутизации по умолчанию:

| Событие | Бот | SMS | E-mail |
|---|---|---|---|
| Код входа / сброса | ✅ | ✅ | ✅ |
| Напоминание об оплате, долг | ✅ | ✅ | ✅ |
| Счёт выставлен, платёж принят | ✅ | — | ✅ |
| Пропуск / опоздание | ✅ | — | — |
| Новая оценка | ✅ (дайджест) | — | — |
| Изменение расписания на сегодня/завтра | ✅ | — | — |
| События школы, предупреждения | ✅ | — | — |

Если у человека нет бота, важное (оплата, коды) уходит в SMS. Остальное ждёт подключения бота.

### 3.9 Дисциплина — основа для v2
- **ViolationType** — справочник нарушений (штраф баллов, тяжесть).
- **DisciplineRecord** — запись о нарушении.
- **MoralScoreEntry** — проводки нравственных баллов (как леджер).
- Права `discipline.*` заведены, но ролям в v1 не выданы. Посещаемость публикует доменное событие «опоздание/пропуск», подписчик дисциплины выключен флагом. Интерфейса в v1 нет.

### 3.10 Отзывы учителей друг о друге (запрос Umid, 24.10.2026)
Учитель по очереди видит карточки коллег, как в приложениях знакомств, и ставит каждому оценку от 1 до 10 или «Не знаю».
- **Без раундов** (решение Umid): на странице «Оцените коллег» всегда лежат учителя своего филиала, которых этот учитель ещё не оценил. Новый учитель сразу появляется на этой странице у всех остальных.
- **FeedbackCycle** — период оценки филиала (Q17): новый период начинается автоматически с новым учебным годом, а директор может в любой момент «запустить всё заново» — тогда все коллеги снова появляются в очереди у всех. Прошлые периоды и их результаты сохраняются.
- **FeedbackResponse** — ответ: филиал, период, кто оценил, кого оценили, оценка 1–10 **или** «Не знаю», комментарий, время. Уникальность: (период, кто, кого). Изменить оценку внутри периода нельзя.
- **Правила:**
  - комментарий обязателен, если оценка ≤ 4 или ≥ 8; при 5–7 и «Не знаю» поля комментария нет. Пороги 4 и 8 — настройки;
  - «Не знаю» не влияет на среднюю. [предложение] Через N дней (настройка, по умолчанию 30) коллега снова появляется в очереди — за это время учитель мог с ним познакомиться;
  - после ответа или «Не знаю» сразу открывается следующая карточка. Себя оценить нельзя; порядок карточек случайный, но у каждого учителя устойчивый; можно прерваться и продолжить;
  - оценивают только учителя, и только учителей своего филиала (Q15);
  - на карточке: фото (или инициалы), ФИО, предметы, классы и группы, классное руководство. Фото — новое необязательное поле сотрудника.
- **Анонимность — полная** (Q13): автор хранится только для защиты от повторов и не показывается никому — ни директору, ни основателю, ни суперадмину в интерфейсе.
- **Результаты видят директор своего филиала и основатель — оба филиала** (Q14, Q18). Учитель свои результаты не видит.
- **Результаты:** по каждому учителю — средняя, число оценок, число «Не знаю», распределение 1–10, комментарии (без авторов). Средняя и распределение показываются, только если оценок ≥ 3 (настройка) — иначе можно угадать автора.

## 7. Критерии готовности v1

- Учитель отмечает посещаемость и ставит оценки на уроке с телефона менее чем за 30 секунд на класс.
- Ни один пользователь не видит данные чужого филиала (автотесты по матрице «роль × операция»).
- Долг ученика = сальдо леджера; аванс гасит следующие счета; отчёт должников сходится с проводками.
- Бот показывает расписание на сегодня и завтра с учётом изменений, внесённых минуту назад.
- Коды входа приходят во все подключённые каналы, включая SMS; SMS не используются для неважных событий.
- Все тексты на uz и ru; все экраны сотрудников работают на ширине 360 px.
- Данные старой системы перенесены и сверены (количество учеников, классов, учителей).
